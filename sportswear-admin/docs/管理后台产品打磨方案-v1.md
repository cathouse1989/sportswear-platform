# 管理后台产品打磨实施方案（v1.0）

> 文档版本：v1.0　　更新日期：2026-08-27
> 问题陈述（原话转述）：目前管理后台没有产品说明书，导致现在开发出来的产品质量不行。
> 本方案回答两件事：**① 为什么会变成这样（根因诊断）；② 怎么把它打磨成一款好产品（路线图 + 过程机制）**。
> 事实依据全部来自代码实测与既有文档，详见姊妹篇《管理后台产品说明书-v1.md》（现状基线 + 已知缺陷清单）。

---

## 一、根因诊断：为什么"没有说明书"必然导致"质量不行"

1. **缺少需求基线 → 功能靠想象堆砌**
   全项目唯一一份需求文档（portal/docs/requirements/系统需求文档.md v1.1）重心在后端与门户；admin 的 21 个页面没有任何 UI 层规格说明。结果是开发等于"看着数据库字段画增删改查"，例如回收站下拉只手抄了 5 种实体类型，漏掉了其余实体。

2. **缺少验收标准 → "能跑就是完成"**
   `views/cms/blogs.vue` 里 script 写好了 `openCreateDialog / handleSave / dialogVisible`，但模板里**根本没有渲染任何 el-dialog**——"新建博客"按钮点了毫无反应，这样的断头功能却能以 73 行代码合入并长期存在。没有 per-page 验收用例，就没有人发现它坏了。

3. **没有前端工程规范 → 质量无法收敛**
   - package.json 只有 dev/build/preview：无 ESLint、无 prettier、无测试；
   - `api/*.ts` 参数与返回大量 `any`，前后端契约靠猜（后端其实有 90+ 个职责清晰的 Admin API + 权限矩阵，但从未生成/同步成前端类型）;
   - 两极分化：21 个页面里 14 个不到 120 行（壳），而 `product/index.vue` 一个文件 1651 行、`portal/preview.vue` 1174 行——没人敢动的巨石文件与随时烂尾的小文件并存。

4. **业务闭环缺失 → "管理"退化成"登记"**
   媒体管理只有元数据 CRUD（MinIO/S3 上传尚未接通，平台评估文档同样列入 P0 遗留）；多语言有 translations 表却无翻译工作流 UI；Sitemap 未自动生成。后台录完的数据不能顺畅地变成前台可卖的内容，业务价值打折。

5. **结论**
   质量差不是某个页面的锅，而是 **"没有说明书 → 没有评审/验收 → 没有规范护栏 → 巨石化 → 更改不动说明书更不敢写"** 的负循环。打破它的支点是：先把"说明书"立起来（已完成，即姊妹篇 v1.0），再用一轮止血 + 地基工程重建正向循环。

## 二、产品质量目标与完成定义（DoD）

### 2.1 北极星场景

> 一名新运营，只拿着本说明书，能在 **30 分钟内**独立完成 1 个产品的完整上架（基本信息/图片/规格/MOQ/英文内容/至少 1 门翻译/SEO），发布后前台四语站点立即可见且通过第七章质检基线。

### 2.2 量化指标

| 维度 | 现状 | 目标 |
|------|------|------|
| P0 级缺陷 | 至少 1 项（博客弹窗缺失） | 清零，且新增零容忍 |
| 核心链路冒烟 | 无 | 登录/建品/发布/前台可见 4 条链路 vitest 自动化 100% 通过 |
| 巨石文件 | product 1651 行、preview 1174 行 | 单文件 ≤500 行（product 拆分为列表 + 编辑抽屉 + 分步组件） |
| API 层类型安全 | any 泛滥 | 由 OpenAPI 生成的类型全量替换 `api/*.ts` any |
| 工程门禁 | 无 lint/测试/CI | vue-tsc + eslint + vitest 进 CI，红灯禁合并 |
| 文档一致性 | 无 | 任何行为变更 PR 必须携带说明书 diff |

### 2.3 统一 DoD（Definition of Done）模板

每个功能任务只有同时满足以下条目才算完成：
① 说明书相应章节已更新；② 附 1 条最小验收用例（步骤+预期）；③ vue-tsc/eslint 零新增告警；④ 关键路径手动自测 + 截图；⑤ 若涉及接口变更，Swagger/类型已重新生成。

#### #2 表单校验与提示规范 ◐ 首批已落地（2026-08-27）

## 四、过程机制：防止再次失控（比排期更重要）

1. **需求流**：任何新菜单/新字段，第一步永远是改《管理后台产品说明书》——PR 描述必须贴出说明书 diff；
2. **评审流**：涉及页面交互的改动附截图或录屏到用例库条目（docs/acceptance/<page>.md）；
3. **门禁流**：CI 红 = 禁合并（vue-tsc + eslint + vitest 冒烟）；P0 级交互缺陷回归当周清零复盘一次；
4. **例行走查**：每周五随机抽 3 个页面对照说明书运行验收用例，漂移即修（30 分钟内的小改动现场处理）；
5. **版本纪律**：说明书随代码发版打 tag（v1.x），重大行为变更列 CHANGELOG。

## 五、依赖、风险与开放问题

**依赖后端/平台的协作项**
- swaggo 注释接入与 OpenAPI 发布（P0-#5 前置）;
- cases/faqs 补 publish/unpublish 端点、Sitemap 生成、App 管理接口就绪度核对（P1）；
- MinIO 预签名直传接口（P0-#4 前置）。

**风险与对策**

| 风险 | 对策 |
|------|------|
| product/index.vue 拆分引入回归 | 先补三条冒烟测试再动刀，拆完跑全量验收用例 |
| 类型生成改造期间 any/手写类型双轨 | 设截止提交，之后 lint 规则 ban-any 于 api 目录强制切齐 |
| 质检基线条款与业务现状冲突 | 第 0 期 W2 会签决定条款取舍，落不进本期规范的移入 backlog 并记录原因 |
| 团队执行力衰减 | 用例库 + 周走查成本极低（每周 ≤1h），关键在固定例会同步 |

## 六、一页纸结论

1. 说明书已补上（姊妹篇 v1.0）：21 个页面逐一实测建档 + 8 项实证缺陷清单 = 一切后续工作的统一基线；
2. 本周只做三件事：修 P0 断头缺陷、会签规范、搭验收用例库骨架；
3. 然后 P0 地基（骨架组件/校验规范/按钮权限/媒体上传闭环/契约硬化/工程护栏）→ P1 闭环打磨（建品向导/翻译工作流/CMS 归一/运营可见性）→ P2 提效；
4. 机制先行：改动必过说明书 diff + 用例 + 门禁三关，让"质量不行"从根因上不再复发。
