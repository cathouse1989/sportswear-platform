# 权限矩阵与接口开放清单

## 一、接口开放分类总览

| 分类 | 路径前缀 | 认证方式 | 说明 |
|------|---------|---------|------|
| **公开接口** | `/api/v1/public/*` | 无需认证（IP 频率限制 30次/分钟） | 面向全球访客，只返回已发布内容 |
| **后台接口** | `/api/v1/admin/*` | JWT + RBAC 权限码硬控 | 商家管理后台 |
| **应用接入** | `X-App-Key` 请求头 | 应用 API Key 校验 | 子应用/第三方系统接入 |

## 五、状态开关体系

### 三层状态控制

| 对象 | 字段 | 禁用效果 |
|------|------|---------|
| **用户** User.Status | active / disabled | 禁用后无法登录，已有 Token 仍有效（建议配合操作日志审计） |
| **角色** Role.IsActive | true / false | 禁用后：该角色用户登录不再获得该角色；每次请求实时校验，禁用立即生效 |
| **应用** App.IsActive | true / false | 禁用后：该应用的 API Key 立即失效，子应用无法接入 |

### 操作接口
```
PUT /api/v1/admin/users/:id          {"status": "disabled"}   # 禁用用户
PUT /api/v1/admin/roles/:id/status   {"is_active": false}     # 禁用角色
PUT /api/v1/admin/apps/:id/status    {"is_active": false}     # 禁用应用
```

## 六、应用维度权限架构（多子应用方案）

### 数据模型
```
apps (应用注册表)
├── code, name, api_key, secret, is_active
│   示例：admin 后台 / customer_portal 客户中心 / mobile 移动端 / third_party 第三方

permissions (权限表)
├── app_id (NULL=平台级权限，否则归属特定应用)

roles (角色表)
├── app_id (NULL=全局角色跨应用可用，否则为应用专属角色)
├── is_active (启用/禁用)

user_roles (用户-角色关联)
├── app_id (NULL=所有应用生效，否则仅该应用生效)

app_users (用户-应用关联)
├── 同一用户在不同应用可有不同授权状态
```

### 子应用接入方式
```
子应用请求时携带：
X-App-Key: sk_xxxxxxxxxxxxxxxx

中间件校验：
1. API Key 是否存在且应用 is_active=true
2. 通过后注入 app_id/app_code 到请求上下文
3. 可结合 RequirePermission 做应用内权限过滤
```

### 扩展路线
- **当前（第一阶段）**：单服务 + 应用维度数据模型 + API Key 接入
- **中期**：如子应用增多，可将认证授权抽离为独立 IAM 服务（OAuth2/OIDC）
- **长期**：引入 Casbin 策略引擎支持更灵活的 ABAC 策略
