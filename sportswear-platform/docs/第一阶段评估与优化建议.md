## 二、本次新增能力

### 1. 日志管理系统
```
logs/
└── 2026-08-22/                    ← 按日期分目录
    ├── app.log                    ← 业务日志（JSON 格式，分级：DEBUG/INFO/WARN/ERROR）
    ├── access.log                 ← 访问日志（流量分析用）
    └── audit/
        └── audit.log              ← 审计日志（后台操作，永久保留）
```

**自动管理能力：**
- 每日 0 点自动切换新日期目录
- 自动清理过期目录（生产保留 30 天，开发保留 7 天）
- 日志级别按环境自动调整（development=DEBUG，production=INFO）
- 所有日志带 `request_id`，支持全链路追踪

### 2. 流量监测系统（商业价值）

**数据采集（VisitLog 表）：**
- 访问者：IP、国家、设备、浏览器、OS、UA
- 访问内容：路径、实体类型、实体 slug、HTTP 状态、延迟
- 来源归因：Referer、Source（google/bing/social/direct）、Medium（organic/cpc/referral）、UTM 参数

**分析维度（6 个统计 API）：**
| API | 商业价值 |
|-----|---------|
| /admin/analytics/overview | 总访问量、独立 IP、询盘转化率、每日趋势 |
| /admin/analytics/top-pages | 哪些页面最受欢迎 → 内容优化方向 |
| /admin/analytics/top-products | 哪些产品最受关注 → 主推产品决策 |
| /admin/analytics/sources | Google/Bing/社媒流量占比 → SEO/广告投放 ROI |
| /admin/analytics/countries | 客户地域分布 → 市场开拓优先级 |
| /admin/analytics/devices | 设备分布 → 前端适配优化 |

### 3. 全链路追踪
```
客户端请求 → X-Request-ID 头（可自定义保持链路）
    ↓
响应体 requestId + 响应头 X-Request-ID
    ↓
业务日志 app.log: {"request_id": "xxx", "level": "INFO", ...}
访问日志 access.log: {"request_id": "xxx", "ip": "...", ...}
审计日志 audit.log: 操作留痕
    ↓
问题排查：拿一个 requestId 即可串联该请求的所有日志
```

## 三、数据一致性管理方案

### 当前机制
| 场景 | 机制 | 状态 |
|------|------|------|
| 内容更新 → 前台可见 | 发布状态实时生效（无缓存层） | ✅ 天然一致 |
| 访问数据写入 | 异步队列（1000 缓冲），不阻塞主流程 | ✅ 及时性保障 |
| 权限变更生效 | 每次请求从 DB 实时加载角色权限 | ✅ 无缓存不一致 |
| 级联删除一致性 | GORM 事务保证，失败回滚 | ✅ |
| Redis 缓存 | 已预留连接（database/redis.go），当前未启用缓存 | 📋 第二阶段 |

### 第二阶段缓存策略建议
```
内容发布 → 清除 Redis 对应缓存键 → 下次请求回源 DB → 写入新缓存
缓存键设计：
  cache:page:{slug}:{lang}     TTL 5min
  cache:product:{slug}:{lang}  TTL 5min
  cache:navigations:{type}     TTL 10min
后台发布/下线/更新时主动失效对应键
```
