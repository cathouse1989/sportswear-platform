# 全球时区处理方案

## 一、核心设计原则

面向全球的网站，时间处理遵循三大原则：

```
1. 存储统一 UTC    —— 数据库所有时间字段统一 UTC，避免多时区混乱
2. 传输统一 RFC3339 —— API 统一返回 ISO8601 + UTC（Z 后缀），无歧义
3. 展示按访客时区  —— 客户端根据访客本地时区自动转换显示
```

## 二、统一标准

### 1. 存储层（数据库）

```sql
-- PostgreSQL DSN 统一配置
TimeZone=UTC

-- 所有 time.Time 字段统一存储 UTC
-- 作用：无论服务器部署在哪个时区，存储的时间基准一致
```

### 2. 传输层（API 响应）

```
统一返回 RFC3339 格式（带 Z 后缀的 UTC 时间）：

"created_at": "2026-08-22T04:39:37.772101Z"
"updated_at": "2026-08-22T07:25:04.24769Z"
"published_at": "2026-08-22T07:25:04.247044Z"

Z 后缀 = UTC 时间，天然无歧义
```

### 3. 展示层（前端）

```
浏览器/App 收到 UTC 时间后，根据用户本地时区自动转换：

纽约用户：2026-08-22T04:39:37Z → 显示 2026-08-22 00:39:37（EDT）
东京用户：2026-08-22T04:39:37Z → 显示 2026-08-22 13:39:37（JST）
```

## 四、时区检测中间件

### 解析优先级

```
1. X-Timezone 请求头（显式指定）
2. tz 查询参数
3. 默认 UTC
```

### 使用示例

```bash
# 默认 UTC
GET /api/v1/time

# 指定时区（请求头）
GET /api/v1/time
X-Timezone: America/New_York

# 指定时区（查询参数）
GET /api/v1/time?tz=Asia/Tokyo
```

### 验证结果（实际运行）

```
utc_now:            2026-08-22T07:36:26Z
timezone (默认):     UTC
local_now (UTC):    2026-08-22T07:36:26Z
local_now (纽约):   2026-08-22T03:36:26-04:00  ✅
local_now (东京):   2026-08-22T16:36:26+09:00  ✅
```

## 五、时间信息接口（公开）

```
GET /api/v1/time

返回：
{
  "utc_now": "2026-08-22T07:36:26Z",          // 服务器 UTC 时间
  "local_now": "2026-08-22T16:36:26+09:00",   // 按访客时区
  "timezone": "Asia/Tokyo",                    // 当前时区
  "common_timezones": [...]                    // 20 个常用时区列表
}
```

前端可用此接口获取服务器时间和时区列表，构建时区选择器。

## 七、数据统计的时区处理

流量分析、询盘统计等时间聚合查询，统一按 UTC 天统计：

```
$today  = StartOfDayUTC(NowUTC())  // 00:00:00 UTC
$tomorrow = EndOfDayUTC(NowUTC())  // 23:59:59 UTC

SQL: WHERE created_at >= $today AND created_at < $tomorrow
```

保证不同时区的访客，统计口径一致（按 UTC 自然日）。

## 八、夏令时（DST）说明

Go 的 `time.LoadLocation` 自动处理夏令时：
- America/New_York 夏季为 -04:00（EDT），冬季为 -05:00（EST）
- Europe/Paris 夏季为 +02:00（CEST），冬季为 +01:00（CET）

工具函数内部使用标准 `time.Location`，DST 自动正确转换，无需特殊处理。
